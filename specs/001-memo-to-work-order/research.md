## 결정 상세

### D1. 혼합 방식 (Q1)

- 결정: LLM은 메모를 읽고 항목 후보(코드, 수량, 근거 문장 번호, 상태, 쟁점)를 JSON으로 낸다. 프로그램은 그 결과를 검사해서 틀린 것은 확인필요로 내린다.
- 이유: 현장 표현이 사전에 다 들어 있지 않아서 규칙만으로는 앞으로 오는 메모를 못 덮는다(추정). 반대로 LLM만 믿으면 헌법 원칙 IV를 지킬 수 없다.
- 검토한 대안: 규칙만(약어 사전과 정규식). 10건에는 맞출 수 있지만 번호가 비어 있어 더 많은 메모가 있을 수 있다(관찰: INS-007, 009, 011~018이 없음). 일반 규칙으로 만들라는 원칙과 맞지 않는다.

### D2. 검사 규칙 (Q5)

모든 규칙은 프로그램이 결과에 대해 실행하고, 걸리면 항목을 확인필요로 내리거나 경고를 남긴다.

| ID | 규칙 | 연결 요구사항 |
|----|------|---------------|
| V1 | 코드표에 없는 코드는 코드 없이 확인필요로 내린다 | FR-003 |
| V2 | 근거 문장 번호가 메모에 없거나 비어 있으면 확인필요로 내린다 | FR-004 |
| V3 | 제안인데 근거 문장에 약한 말투("권장", "~할 듯", "~나을 것 같음", "점검 필요")가 있고 지시 말투가 없으면 확인필요로 내린다. 말투 사전을 쓴다 | FR-005 |
| V4 | `-EX`(교환) 코드가 제안인데 근거에 교환을 말하는 단어가 없으면 확인필요로 내린다 | FR-005 |
| V5 | 수량 단위가 어긋날 수 있는 코드(타이어는 2 초과, 브레이크는 앞뒤 불명)는 확인필요로 내린다 | FR-011 |
| V6 | 같은 코드가 중복되면 한 항목으로 합치고 근거를 모은다 | FR-009 |
| V7 | 전체 결과가 판단불가이면 제안이 0개여야 하고, 작업없음이면 항목이 0개여야 한다 | FR-008, FR-002 |
| V8 | 어떤 항목에도 연결되지 않은 문장이 있으면 누락 경고를 낸다 | FR-013 |
| V9 | 작업을 말하는 문장이 사라졌으면 코드없음 항목으로 되살린다 | FR-007 |
| V10 | 코드가 없는데 대안이 있는 항목은 확인필요로 두고 첫 대안을 추천으로 올린다 | FR-006 |
| V11 | `판금도색` 코드는 근거에 판금이 없으면 확인필요로 내린다 | FR-005 |

이 목록은 `추정`이다. 10건을 돌려 보며 다듬은 것이라, 처음 보는 메모에서 맞는지는 확인하지 못했다. 일부 규칙(V3, V4, V11)은 코드표 이름과 단어 목록에 기대므로 일반성은 확인하지 못했다.

### D3. 프로그램 검사로 막지 못하는 것

- 도색 범위(광택이 부분인지 전체인지) 같은 의미 판단은 프롬프트에 기대고 프로그램이 막지 못한다. 설계 문서에 한계로 적는다.
- 반복 실행 편차는 아직 측정하지 않았다(Q11).

### D4. 호출 비용 (Q2)

관찰: 첫 호출의 `total_cost_usd`는 약 0.11달러(캐시 생성 27,683토큰), 같은 형태의 두 번째 호출은 약 0.003달러였다. 10건을 한 번 돌리는 데 드는 비용은 캐시 여부에 따라 달라진다. 정확한 총비용은 구현에서 측정해 README에 적는다.
