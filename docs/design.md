# 설계 문서

검수 메모를 읽고 표준 작업 코드를 골라 오더를 만드는 일에서, 읽기와 찾기와 입력은 기계가 하고 해석과 확신의 책임은 사람에게 남기도록 만들었습니다. 확실한 항목은 제안하고, 애매한 항목은 근거 문장과 추천 코드를 붙여 관리자에게 넘기며, 최종 승인은 항상 사람이 합니다.

결과를 보려면 `report.html`을 브라우저로 열면 됩니다. 실행 방법은 README에 있습니다.

## 1. 김OO님의 5분은 무엇으로 이루어져 있다고 보았나

현장에서 재 본 숫자가 없어서 이 절은 가정입니다. 5분을 세 덩어리로 나누어 보았습니다.

| 덩어리 | 내가 본 크기 | 이유 |
|---|---|---|
| 메모 읽기 | 작다 | 메모는 두세 문장이고 가장 긴 것도 네 문장이다 (제공된 10건 기준) |
| 코드 찾기 | 작다 | 코드는 35개이고 이름에 부위와 작업이 들어 있다 |
| 입력 | 작다 | 고른 코드와 수량을 옮겨 적는 일이다 |
| 해석과 확신 | 크다 | "교체 권장"이 지시인지, "프싸"가 어느 부위인지, 트레드 2mm를 갈아야 하는지는 읽는다고 풀리지 않고 판단이 필요하다. 틀리면 현장에서 그대로 작업이 진행된다 |

병목은 앞의 세 개가 아니라 마지막 하나라고 판단했습니다. 앞의 세 개는 기계가 거의 0으로 만들 수 있지만, 마지막은 줄일 수는 있어도 없앨 수는 없고, 없애서도 안 됩니다. 책임이 걸려 있기 때문입니다.

그래서 이 가정이 틀렸을 때를 대비해 성공 기준(4번)의 첫 항목에 "도입 전 시간을 먼저 잰다"를 넣었습니다.

## 2. 무엇을 공략하고 무엇은 하지 않기로 했나

**공략한 것**

- 읽기, 찾기, 입력: 메모 한 건을 넣으면 코드, 수량, 근거 문장이 붙은 초안이 나옵니다.
- 해석의 부담: 애매한 항목은 쟁점 한 줄, 추천 코드, 대안, 근거 문장을 붙여 관리자가 고르기만 하면 되게 했습니다. 해석을 대신하지는 않고, 해석에 필요한 재료를 모아 줍니다.

**하지 않은 것과 이유**

| 하지 않은 것 | 이유 |
|---|---|
| 확신 퍼센트 표시 | 근거 있는 숫자를 만들 수 없다. 90%라고 보여 주면 사람이 확인을 건너뛴다 |
| 전부 자동 승인 | 한 건에 수십만 원이 걸려 있고 틀렸을 때 되돌릴 수 없다 |
| 검수자가 메모를 쓰는 순간 되묻기 | 검수자의 일하는 방식을 바꿔야 해서 3시간 범위를 넘고, 현장이 받아들일지 모른다 |
| 사람별 말버릇 학습, 규칙 자동 승격 | 이번 범위가 아니다 |
| 벡터 검색 | 코드가 35개뿐이라 전부 프롬프트에 넣을 수 있다. 검색 단계를 더하면 틀릴 곳만 는다 |
| 규칙만으로 풀기 | 10건 안에서도 표현이 제각각이고("프싸", "뎁흠", "도색보다 교환이 나을 것 같음") 번호가 중간에 비어 있어 더 많은 메모가 있을 수 있다. 사전과 정규식으로는 앞으로 올 표현을 못 덮는다 |
| 로그인, DB, 배포, 정비소 시스템으로의 전달 | 이번 과제의 판단과 거리가 멀다 |
| 성공 지표를 재는 기능 | 배포하지 않으므로 만들지 않았다. 지표는 4번에 글로만 적었다 |

**LLM을 쓴 이유와 규칙과의 비교**

해석은 LLM(Claude)이 하고, 그 결과를 프로그램이 검사합니다. LLM만 믿으면 코드표에 없는 코드나 메모에 없는 근거가 섞일 수 있고, 규칙만 쓰면 새 표현을 못 읽습니다. 그래서 해석은 LLM에게, 검증은 프로그램에게 맡겼습니다. 프로그램 검사 규칙은 11개입니다(코드표에 없는 코드, 근거 문장 번호, 약한 말투, 교환 근거어, 수량 단위, 중복 병합, 전체 결과 모순, 연결 안 된 문장, 사라진 작업 복원 등).

## 3. 결과가 틀렸을 때는 무슨 일이 생기나, 사람 확인은 어디에 두었나

**피해**: 안 해도 될 도색을 하거나, 해야 할 교체를 빠뜨립니다. 한 건에 수십만 원입니다.

**막는 방법은 세 겹입니다.**

1. LLM은 확실하지 않으면 "확인필요"로 두도록 지시받습니다. 원칙은 "애매하면 넘긴다"입니다.
2. 프로그램이 결과를 다시 검사해서, 틀렸거나 애매한 제안은 확인필요로 내립니다. 위로 올리는 일은 없습니다.
3. 사람 확인 지점이 두 곳 있습니다.
   - 확인필요 항목을 하나씩 고르거나 "이 작업은 하지 않음"을 고릅니다.
   - 최종 승인입니다. 확인필요가 하나라도 남아 있으면 승인 버튼이 잠기고, 서버도 거절합니다(409). 코드표에 없는 코드도 서버가 다시 거절합니다(422). 승인한 오더는 덮어쓰지 못합니다.

**해석에 실패하면**(오류나 응답 없음) 한 번 더 시도하고, 그래도 안 되면 해석 없이 메모 문장만 나열하고 전부 확인필요로 둡니다. 코드는 하나도 제안하지 않습니다. 시스템이 못 읽어도 관리자는 지금과 같은 상태로 돌아갈 뿐 손해가 없습니다.

**남는 위험**: 제안 항목은 한 번에 승인할 수 있어서, 확인 없이 승인만 누르면 틀린 제안이 나갈 수 있습니다. 그래서 제안 항목에도 근거 문장을 항상 같이 보여줍니다. 이 위험은 막지 못했고, 막으려면 사람이 훑어본 것을 확인하는 장치가 필요한데 이번에는 넣지 않았습니다.

## 4. 성공을 무엇으로 측정하겠나

**성공 기준: 관리자가 한 건의 오더를 만드는 시간이 도입 전보다 짧고, 틀린 오더가 현장까지 나간 건수가 0건이다.**

- 기준선은 도입 전 2주 동안 같은 관리자가 같은 방식으로 한 건당 걸린 시간을 재서 정합니다. 지금 5분이라는 값이 실제로 잰 값인지 알 수 없어서, 이 값을 믿지 않고 먼저 재는 것으로 시작합니다.
- 도입 후 2주 동안 같은 방식으로 재서 비교합니다. 기준선보다 짧으면 시간 기준은 통과입니다. 목표 시간(몇 분 이하)은 정하지 않았습니다. 근거 없는 숫자를 만들고 싶지 않았고, 아무리 작아도 기존보다 짧으면 이득이라고 보았습니다.
- 틀린 오더가 1건이라도 현장까지 나가면, 시간이 줄었어도 실패로 봅니다.

이번 과제에서는 배포하지 않으므로 시간을 재는 기능은 만들지 않았습니다. 대신 제공된 10건으로 "잘못 확정" 건수를 측정했습니다. 이것은 2주 측정을 대신하지 않고, 사전 점검입니다.

## 5. 가정 목록

| 번호 | 가정 | 틀렸을 때 |
|---|---|---|
| A1 | 5분은 읽기, 찾기, 입력이 작고 해석과 확신이 크다 | 1번과 4번이 바뀐다. 4번이 이 가정을 먼저 재도록 만들었다 |
| A2 | 항목 상태 이름(제안, 확인필요, 코드없음)과 메모 전체 결과(정상, 작업없음, 판단불가)는 우리가 정한 것이다 | 현장 용어에 맞춰 바꾼다 |
| A3 | 정답표는 우리가 메모를 읽고 만든 해석이다 | 평가 결과는 "우리 해석과 일치"로만 읽는다 |
| A4 | 기본 문서의 말투 사전(지시와 권장의 구분)은 과제 자료에서 확인한 것이 아니라 우리가 정했다 | 확인필요가 늘거나 줄 수 있다 |
| A5 | 보강 문서의 현장 약어와 판단 기준("프싸"=우측 앞휀다, 운전석=좌측, 트레드 3mm 이하=교환 등)은 가정이다 | 보강본 결과는 점수에 넣지 않았다 |
| A6 | 승인한 오더를 정비소 시스템으로 보내는 일은 범위 밖이다 | 연동 설계가 필요하다 |
| A7 | 사용자는 승인하는 관리자이고, 검수자는 지금처럼 메모만 쓴다 | 검수자 입력 보조는 다른 설계가 된다 |
| A8 | 메모는 10건이지만 번호가 중간에 비어 있어 더 많은 메모가 있을 수 있다. 규칙은 이 10건에 맞춘 땜질이 아니라 일반 규칙으로 만들었다 | 처음 보는 메모에서의 정확도는 재지 못했다(6번) |

## 6. 현장에 물을 질문

1. "프싸"는 어느 부위인가. 방향 없는 "휀다"는 앞휀다인가.
2. 운전석은 좌측으로 보면 되는가.
3. 트레드 몇 mm부터 타이어를 교환하는가. 브레이크 패드는 몇 mm부터인가.
4. "1짝"은 타이어 몇 개인가.
5. 광택이 일부 부위만 적혀 있으면 전체 광택 코드로 처리하는가.
6. 어떤 말투가 지시이고 어떤 말투가 추천인가. 검수자마다 다른가.
7. 메모 중 번호가 비어 있는 것(INS-007, 009, 011~018)은 어떤 메모인가. 더 있는가.
8. 지금 한 건에 5분이라는 값은 어떻게 재었는가.
9. 코드표에 없는 작업(점검, 썬루프 소음 같은 것)은 현재 어떻게 처리하는가.

## 7. 어디까지 만들었고, 결과는 어떤가

**만든 것**: 메모 한 건을 오더 초안으로 바꾸는 해석과 검사, 확인필요를 고르고 승인해 확정 오더를 저장하는 화면과 서버, 정답표 평가, 기본/보강 문서 비교, 서버 없이 열리는 `report.html`입니다. 결과 데이터 구조는 `specs/001-memo-to-work-order/data-model.md`에 있습니다.

**제공된 10건의 결과** (기본 문서, `python -m src.evaluate`)

| 항목 | 숫자 |
|---|---|
| 제안 / 확인필요 / 코드없음 | 5 / 10 / 3 |
| 잘못 확정 | 0 |
| 빠뜨린 제안, 지나친 확인필요 | 0, 0 |
| 묻힌 쟁점 | 1건 (INS-003의 타이어 상태가 확인필요가 아니라 코드없음으로 나왔다) |
| 코드없음 개수 불일치 | 1건 (같은 건) |
| 전체 판정 불일치 | 0 |

문서(용어집, 규칙, 말투 사전)를 보강하면 제안이 5개에서 10개로 늘고 확인필요는 10개에서 5개로 줄었습니다(INS-003, 004, 006, 008, 020이 달라졌습니다). 보강본은 가정이 들어 있어 점수에 넣지 않았습니다. 정답표는 우리 해석이므로, 위 숫자는 "회사의 정답과 일치"가 아니라 "우리 해석과 일치"입니다.

## 8. 한계

- **10건을 보고 다듬었습니다.** 첫 실행에서 광택이 제안으로 나온 것(용어집과 규칙이 서로 어긋났다), 점검 작업에 교환 코드를 추천한 것, 증상이 구체적인데 판단불가로 나온 것을 보고, 용어집 한 줄과 프롬프트 지침 두 개를 고쳤습니다. 일반 규칙으로 적었지만 10건에 맞춰진 부분이 있을 수 있습니다. 처음 보는 메모에서의 정확도는 재지 못했습니다.
- **정답표는 우리 해석입니다.** 지원자가 검토해 확정했지만, 회사의 정답이 아닙니다.
- **같은 메모를 다시 돌리면 일부가 달라집니다.** 10건을 세 번 돌려 비교하니 8건은 완전히 같았고, INS-003(타이어)과 INS-008(앞유리)이 달랐습니다. 달라진 것은 확인필요와 코드없음 사이의 분류였고, 제안 5개는 세 번 모두 같았습니다. 항목 단위로는 18개 중 17개가 같았습니다. 세 번만 재서 이 이상은 말하지 못합니다. LLM 호출에는 온도 설정이 없어서 같게 만들 방법도 없었습니다.
- **프로그램이 막지 못하는 것이 있습니다.** 광택이 부분인지 전체인지, 점검과 교환의 구분 같은 의미 판단은 프롬프트에 기대고 있습니다.
- **말투 검사는 단어 포함 여부입니다.** "교체 권장하지 않음"처럼 부정이 붙어도 약한 말투로 읽어 확인필요로 내립니다. 안전한 쪽으로 틀리지만 확인필요가 불필요하게 늘 수 있습니다.
- **로그인이 없습니다.** 승인자 기록과 호출 횟수 제한도 없습니다. 로컬에서만 켜는 시연용이고, 실제 도입에는 승인자 기록이 필요합니다.
- **제안을 확인 없이 승인하는 위험**은 3번에 적은 대로 남아 있습니다.
- **비용**: 10건을 한 번 돌리는 데 0.13~0.19달러가 들었습니다(첫 실행은 캐시가 없어 0.61달러).
