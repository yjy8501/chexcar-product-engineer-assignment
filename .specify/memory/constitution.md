# CHEXCAR 메모-작업코드 매핑 Constitution

## Core Principles

### I. 애매하면 확인필요로 넘긴다 (NON-NEGOTIABLE)

정확히 하나의 표준 코드로 고를 수 없으면 MUST 확인필요로 넘긴다. 추측해서 제안하지 않는다.
메모에 약한 말투("권장", "~할 듯", "점검 필요")가 있거나, 수량이나 위치가 빠졌거나, 코드표에 맞는
코드가 없으면 이 원칙을 적용한다.
이유: 오더가 틀리면 현장에서 그대로 작업이 진행되고 한 건에 수십만 원이 걸린다. (출처: 과제 문서, 명시)

### II. 잘못 확정한 건수는 0이다

시간 단축보다 정확성이 먼저다. 평가에서 "잘못 확정"이 1건이라도 나오면 MUST 단축 효과를 주장하기
전에 원인부터 고친다. 확신 퍼센트 같은 근거 없는 숫자는 보여주지 않는다.
이유: 읽기, 코드 찾기, 입력은 기계가 줄일 수 있지만 해석과 확신의 책임은 사람에게 있다. (출처: 사용자 결정)

### III. 최종 승인은 사람이 한다

시스템은 제안만 한다. 오더는 MUST 관리자가 승인해야 확정된다. 확인필요 항목이 하나라도 남아
있으면 승인할 수 없다. 추천 코드는 보여주되 고르는 것은 사람이다.

### IV. LLM의 답은 프로그램이 검사한다

LLM은 메모를 해석만 한다. 코드표에 없는 코드, 메모 원문에 없는 근거 문장은 MUST 프로그램이
걸러내고 해당 항목을 확인필요로 내린다. 안전은 LLM의 일관성이 아니라 프로그램 검사에 둔다.
검사로 막지 못하고 프롬프트에 기대는 규칙은 문서에 그렇게 밝힌다.

### V. 모든 항목에 근거를 붙인다

항목마다 근거가 된 메모 문장을 MUST 붙인다. 하지 않기로 한 항목도 제외 항목으로 이유와 함께 남긴다.
어떤 항목에도 연결되지 않은 메모 문장이 있으면 누락 경고를 낸다.

## 제품 제약

- 규칙은 주어진 10건에 맞춘 땜질이 아니라 일반 규칙으로 만든다. 번호가 중간에 비어 있어
  더 많은 메모가 있을 수 있다. (출처: 데이터 관찰)
- 정답표는 우리가 만든 해석이다. 평가 결과는 "회사의 정답과 일치"가 아니라 "우리 해석과 일치"로
  쓴다.
- 용어집, 규칙, 말투 사전은 파일로 분리한다. 기본본은 문서에서 근거를 찾은 것만, 보강본은 가정을 넣은
  것으로 나누고 보강본은 점수에 넣지 않는다.
- 제공받은 입력(`data/inspections.json`, `data/work_codes.csv`)은 수정하지 않는다.
- 범위는 작게 유지한다. 사람별 학습, 확률 표시, 벡터 검색 등 고도화는 제출물에 넣지 않는다.
- 저장된 결과로 API 키나 CLI 없이도 화면을 볼 수 있어야 한다.

## 작업 방식

- 순서는 constitution, specify, clarify, plan, tasks, implement를 지킨다. 단계를 건너뛰지 않는다.
- 권장 소요는 3시간이므로 과하게 키우지 않는다.
- 사용자에게 보고할 때는 쉬운 한국어로 쓴다. 문서에 이모지를 쓰지 않는다.
- 커밋, 푸시, 제출처럼 밖으로 나가는 동작은 사용자가 요청한 뒤에만 한다.
- 확인하지 못한 것(처음 보는 메모, 반복 실행 편차 등)은 완료 보고에 그대로 적는다.

## Governance

- 이 constitution은 다른 작업 방식보다 우선한다. 수정은 변경 이유와 함께 이 파일에 기록한다.
- 버전은 의미 있는 변경에 따라 MAJOR(원칙 삭제나 재정의), MINOR(원칙이나 섹션 추가), PATCH(문구 정리)로 올린다.
- plan 단계에서 Constitution Check로 위반 여부를 확인하고, 위반이 있으면 정당한 이유를 적는다.
- 아래 근거 원칙(E1~E4)도 같은 효력을 가진다.

## 근거 원칙 (Evidence Principles)

이 섹션은 evidence-sdd 프리셋이 추가한다. 위 원칙과 함께 모든 산출물(spec, plan, research, tasks, 구현 보고)에 적용한다.

### E1. 출처를 붙인다 (Tag the Source)

- 요구사항과 조사 결론은 MUST 아래 출처 중 하나로 표시한다.
  - `명시`: 사용자 요청, 기획서, 계약서 등에 적혀 있음 (어디에 적혀 있는지 함께 적는다)
  - `관찰`: 코드, 설정, 로그, 트래픽 등에서 직접 확인함 (`파일:줄` 같은 위치를 함께 적는다)
  - `추정`: 근거 없이 합리적인 기본값으로 채움
  - `미확인`: 아직 모름
- `추정`을 `명시`나 `관찰`처럼 쓰지 않는다.

### E2. 범위 없이 "없다"고 하지 않는다 (Bounded Absence)

- "사용처 없음", "영향 없음" 같은 부재 주장은 MUST 확인한 범위(경로, 모듈, 저장소, 검색어)를 함께 적는다.
- 확인하지 않은 범위는 `없음`이 아니라 `미확인`이다.

### E3. 질문 목록으로 시작해서 질문 목록으로 끝낸다 (Question Ledger)

- 조사는 질문 목록으로 시작하고, 끝날 때 각 질문을 `답변됨` / `부분 답변` / `미해결`로 표시한다.
- `미해결` 질문이 남아 있으면 MUST 완료라고 보고하지 않고, 남은 질문을 그대로 보고한다.

### E4. 검증이 통과해야 완료다 (Verified Done)

- 모든 MUST 요구사항은 MUST 최소 1개의 검증(자동 테스트, 또는 자동화가 불가능하면 재현 가능한 수동 절차)에 연결된다.
- 태스크와 요구사항은 그 검증이 실제로 실행되어 통과한 뒤에만 완료로 표시한다.
- "구현했다"는 보고는 근거가 아니다. 실행한 명령과 결과가 근거다.
